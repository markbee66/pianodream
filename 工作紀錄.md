### 「每次開啟都要按信任」—— 排除了 SmartScreen，指向防火牆

使用者回報看到的是「開啟檔案 - 安全性警告」。**實測結果與這個指認不符**：

- `G:`（Google Drive）是 `DriveType=3`（Fixed，非網路磁碟機）、**FAT32**。
  FAT32 沒有交替資料流，**存不住 `Zone.Identifier`**。
  `Get-Item 'G:\…\加樂譜.bat' -Stream *` 回傳空；
  對照組 `C:\Users\micha\Downloads\Bad Apple.pdf` 則有 `Zone.Identifier`。
- 在 `G:` 上放一個測試 .bat，用 `UseShellExecute = true` 啟動（跟 Unity 一樣的呼叫），
  **沒有任何視窗跳出來**，行程乾淨結束。
- `HKCU\…\Policies\Associations`（LowRiskFileTypes）與 `Policies\Attachments`
  都不存在，是預設值。

反過來，**防火牆裡確實有兩條 `Query User{GUID}` 規則**指向本專案用的
Microsoft Store Python，而這種規則**只會**由「Windows 安全性警訊 —— 允許存取」
那個對話框產生。使用者原本的說法是「信任此程式」，那更像這一個。

**還沒證實**：沒能親眼重現使用者看到的視窗。跑真正的 `加樂譜.bat` 時也沒有跳窗。

#### 做了什麼

1. **`音遊/Assets/Scripts/RhythmGame/SongSelectUI.cs` 的 `OpenScoreInput()`**
   從 `UseShellExecute = true` + `FileName = <bat>` 改成
   `UseShellExecute = false` + `cmd.exe /c "<bat>"`。
   ShellExecuteEx 是 AES 與 SmartScreen 的入口，`CreateProcess` 不是。
   已實測 `cmd /c "<含空白的路徑>"` 的引號處理正確、工作目錄正確。
   Unity 沒有主控台，但 `CreateProcess` 會自動配一個給子行程，視窗照樣看得到。
   **未實測**：沒有從真正的 Unity 編輯器按過那個按鈕。

2. **新增 `一次設定.bat` + `一次設定.ps1`**（專案根目錄，跟 `加樂譜.bat` 同層）。
   自己要管理員權限，然後做三件事：解除封鎖、加防火牆放行規則、做桌面捷徑。

   **桌面捷徑指向 `cmd.exe`，把 `加樂譜.bat` 當參數傳**，不是直接指向那個 .bat。
   被安全檢查的是捷徑的目標，而 `cmd.exe` 在 System32、有微軟簽章，永遠不會被攔。

   **關鍵細節：Store 版 Python 要加的是「真實映像路徑」，不是 `sys._base_executable`。**

       sys._base_executable  →  …\Local\Microsoft\WindowsApps\PythonSoftwareFoundation.Python.3.11_…\python.exe
       GetModuleFileNameW    →  C:\Program Files\WindowsApps\…_3.11.2544.0_x64__…\python3.11.exe

   前者是執行別名，防火牆比對的是後者 —— 而現有那兩條 Query User 殘規則
   指的正是後者。只加別名等於沒加。腳本用 `ctypes` 問行程自己拿真實路徑。
   **這個路徑含版本號，Store 更新 Python 之後會對不上，那時要重跑一次設定。**

   腳本也會刪掉舊的 Query User 殘規則（那些會蓋過新加的放行規則）。

   **已實測**：`一次設定.ps1` 在非管理員身分下跑過，第 1 段（FAT32 正確回報
   不適用）與第 3 段（桌面捷徑）都正常，第 2 段正確地跳過並列出五個要放行的程式
   （venv python、執行別名、真實映像路徑、Audiveris 的 java 與 javaw）。
   捷徑產出後也驗過 `TargetPath` / `Arguments` / 工作目錄都對，
   而且捷徑與目標都沒有 `Zone.Identifier`。
   **未實測**：`netsh advfirewall` 那幾行沒有真的跑過（要管理員權限，
   而 UAC 需要使用者自己按）。

   #### 可攜性：這個設定不能只在原作者的機器上有效

   腳本裡**沒有任何寫死的絕對路徑**（`Join-Path $env:SystemRoot` 那種除外）。
   每一項都是執行當下問出來的：

   | 要找的東西 | 怎麼問 |
   |---|---|
   | 專案根目錄 | `$PSScriptRoot` |
   | venv 的 python | `$root\.venv\Scripts\python.exe` |
   | 底層直譯器 | 問 python：`sys._base_executable` |
   | 真實映像路徑 | 問行程自己：`ctypes` → `GetModuleFileNameW` |
   | Audiveris | 問專案自己：`audiveris._default_home()` |
   | 桌面 | `[Environment]::GetFolderPath("Desktop")`（認 OneDrive 轉向） |

   **Audiveris 那一項原本是寫死的三個候選路徑，後來改成呼叫專案自己的
   `_default_home()`。** 各寫一份清單的話，換一台機器就會出現
   「OMR 找得到 Audiveris、但設定腳本沒幫它開防火牆」—— 而且那個函式還認
   `AUDIVERIS_HOME` 環境變數，自己抄一份一定會漏掉。

   防火牆規則與桌面捷徑本來就是「每台機器各自一份」的東西，不可能放進版控 ——
   所以模式是**每個使用者在自己的機器上跑一次**，`開始這裡.md` 也是這樣寫的。
   相對地，`SongSelectUI.cs` 那個改動是程式碼，跟著專案走，所有人都直接生效、
   不需要任何設定。

   #### 過程中修掉的三個真 bug

   - **第一版的本機啟動器被編碼寫壞了。** 用 `[Text.Encoding]::ASCII` 寫入，
     把中文路徑整條變成 `?????`，產出的 .bat 根本不能跑。
     改成不產生中間檔（捷徑直接指向 `cmd.exe` + 參數）——
     .lnk 的參數欄位是 UTF-16，沒有這個問題。腳本會自己清掉舊的壞檔。

   - **`加樂譜.bat` 在非 950 字碼頁下會壞掉（既有 bug，這次才浮出來）。**
     那個檔是 Big5 存的，而 Big5 有些字的第二個位元組正好是 cmd 的特殊字元 ——
     「會」是 `B7 7C`，`7C` 就是管線符號 `|`。主控台字碼頁不是 950 時，
     cmd 會把那幾行從中間切成管線指令，冒出
     `'自動打開...' is not recognized as an internal or external command` 然後啟動失敗。
     以前不會遇到是因為雙擊時字碼頁本來就是 950；但新的 `一次設定.bat`
     開頭有 `chcp 65001`，而且現代終端機常常是 UTF-8。
     修法是在 `@echo off` 後面釘一行 `chcp 950 >nul`。
     **實測**：修之前從 UTF-8 主控台啟動必失敗，修之後
     `cmd /c "<bat>"` 從同一個 UTF-8 主控台啟動，伺服器正常起來、
     `http://127.0.0.1:5000/` 回 200。

3. `開始這裡.md` 第十節加了「第一次要先跑一次 `一次設定.bat`」。

## 2026-08-16 — 連音修復做完了，順帶抓到游標模型的系統性誤判

交接書（`交接_連音修復.md`）2a / 2b 兩項都做完並驗過。**但真正的收穫不是連音，
是查連音時撞到的另一件事。**

### 真正的成因：homr 的交錯排版讓游標模型算出沒有意義的數字

〈山魔王的宮殿〉第 48 小節：

    voice 1 = 4.0 拍　　voice 5 = 4.0 拍　　游標 = 4.5 拍　　拍號 4/4

**兩個聲部都剛好填滿，這一小節沒有任何問題**，卻被判成拍數不對。

原因是 homr 產出的大譜表是「上行一個音 → backup → 下行一個音」一路交錯排的，
backup 的位置常常不對。MusicXML 的正式語意（游標模型）照著走就會走出一個
毫無意義的長度，而各聲部自己其實都是對的。

全 12 首量下來，**534 個「游標判壞」的小節裡有 44 個（8%）是這種誤判**：

    Rush E 19　RushE 手動1 19　Moonlight 3　Peer Gynt 2　給愛麗絲 1
    Alkan / うまぴょい / 士兵 / Andre / Bach / 李斯特 / 蕭邦　0

〈Rush E〉一首就佔 19 個 —— 它的可靠度從 71% 跳到 83%，**一行程式碼都沒改到
辨識，只是不再誤報**。

判準改成 `timing.is_complete()`：**游標對、或每一個聲部各自都對**。
這是**只會變寬、不會變窄**的條件（`cursor_ok OR voices_agree`），
所以不可能新判任何一個小節有問題 —— 校正集那三首 100% 的曲子完全不受影響。

### 連音群只被標了一半：真的存在，但機會很少

交接書的診斷完全正確。〈山魔王的宮殿〉42–48 那連續七個小節，譜上那個 `3`
底下是一條橫跨十幾個音的長連桁，homr 只標了其中三個音。

但**掃過全 12 首，「補完之後總長剛好對得上」的只有 7 個聲部**：

    Peer Gynt m42 m43 m46 m47　李斯特 m49 m60　蕭邦 m69

其中蕭邦 m69（5:4 補 2 個）不是完整的連音群，依 `TUPLET_WHOLE_GROUPS`
放棄 —— 從五連音裡挑兩個標成連音，拍數湊對了、音樂是錯的，
那正是 `_find_triplet()` 早就踩過的坑。

實際生效 5 個聲部。**這條路的天花板就是這麼低**，不要期待它能拉動大盤。

## 2026-08-16 — 拍數錯誤的成因：四個假設，三個被實測否定

homr 的拍數錯誤（`BAD_DURATION`）是目前可靠度的主要瓶頸（李斯特 43%、
蕭邦 11%）。針對「到底是什麼害的」測了四個假設。**否定的結果寫在這裡，
是為了不要再花機器時間重做一次。**

實驗腳本在 scratchpad（`pedal_ab.py`、`ottava_ab.py`、`duration_confusion.py`），
做法都是 A/B：同一批圖跑兩次，只差有沒有把某種記號塗白，比 `BAD_DURATION` 數量。

### ❌ 假設一：`Ped.` 踏板記號被誤讀成音符 —— 否定

相關性看起來很強（有踏板的小節壞掉率高 7～15 個百分點，李斯特的「多認」
小節有 57% 帶踏板、「漏認」只有 22%），但**因果實驗是虛無的**：

    李斯特 13 頁，蓋掉 94 個踏板記號
    壞掉 104/131 -> 102/131　（79.4% -> 77.9%，差 -1.5 個百分點）
    11 頁裡有 8 頁完全沒變

先前的相關性是混淆 —— 踏板記號出現在最濃密的段落，而濃密的段落本來就難讀。

踏板座標的取得方式（之後若要重用）：Audiveris 的 MusicXML 會給
`<pedal default-x default-y>`，單位是 tenths（10 = 一個譜線間距）。
**錨點是 `Ped.` 字樣的左下角，字往上長約 2.2 個間距** ——
上下對稱地蓋會蓋到空白卻漏掉字本身（實測踩過）。
`default-y` 的基準是所屬譜表最上面那條線，要自己從圖上找譜線，
**不能拿小節框的上下緣代替**（見下）。

### ❌ 假設二：音符太密就讀不動 —— 否定

同一首曲子裡比較壞掉與正常小節的音符數中位數，倍率從 0.50 到 1.43，
**沒有一致方向**（蕭邦壞小節密 1.43 倍，但 Andre 小奏鳴曲反而是 0.50 倍）。

### ⚠️ 假設三：`8va` 虛線干擾 —— 測不準，但看不出效果

    李斯特 13 頁，壞掉 110/144 -> 111/145　（+0.2 個百分點）

而且**這個實驗本身有缺陷**：塗掉 8va 之後 homr 切小節的方式變了
（page 4 從 14 節變 18 節、page 6 從 7 變 5），分母不一致就不能直接比。
另外 Audiveris 對 8va 只給起點、**一個 stop 都不給**，跨度只能猜。

### ✅ 假設四：空心符頭（全音符／二分音符）比較容易被讀錯 —— 有支持

533 個拍數錯誤的**誤差大小分佈**：整數誤差佔 40%，其中 `±2 拍` 有 86 個（16%），
是最高峰之一。2 拍正好是全音符與二分音符的差；八分／十六分混淆只會產生
±0.25、±0.5。

含空心符頭的小節比例，隨誤差型態單調變化：

    全部小節        33%   <- 基準線
    ±2 拍誤差       45%   <- 高於基準
    其他整數誤差     40%
    非整數誤差       30%   <- 低於基準

**但反證也很硬**：拿標準答案逐音對齊比對（`duration_confusion.py`），
在乾淨的譜上時值是全對的 ——

    bach_aria515     配對 96 音，時值全部正確
    bach_chorale511  配對 125 音，只錯 2 個（全音符 1/1 正確）
    bach_chorale510  配對 107 音，只錯 1 個

所以正確的說法**不是**「AI 分不出全音符」，而是「在複雜的譜上，空心符頭
比實心符頭更容易被讀錯」—— 空心與否靠的是「中間是不是空的」這個細節，
在音符擠在一起、加線與符桿交錯的地方，這個細節最先糊掉。

**要釘死它還缺一份「有標準答案而且困難」的譜。** 校正集裡有 MIDI 答案的
九首全是簡單的；困難的五首（李斯特、蕭邦、Rush E、Peer Gynt、BWV849）
只有 PDF、沒有答案。

### 順帶抓到的真 bug：小節框的下緣切在低音譜表中間

畫遮罩預覽時發現的。`measure_map` 的小節框**不涵蓋完整的大譜表** ——
下緣切在低音譜表中間，`Ped.` 更是完全在框外。照著框裁圖會把左手切掉一半。

這讓網頁「逐小節校對」的原圖裁切一度是壞的（`web/app.py` 的
`measure_image`）。已修：下緣改成往下延伸到**下一行開始之前**
（踏板、力度、表情記號都住在行間空白裡），上緣反而要收緊，
不然會把前一行垂下來的音符拉進畫面。

**Unity 檢討畫面的照片框可能有同樣問題，還沒查。**

## 2026-08-16 — 這台機器的硬體限制：量過的五個死路

**這一則專門記「換一台機器就可能不一樣」的結論。** 其餘失敗（切段、換引擎）
是模型與演算法本身的性質，跟硬體無關，記在另一則。

量測環境：

    Windows 11 (10.0.26200)   Python 3.11.9
    i7-11800H  8 核 / 16 執行緒
    RAM 15.7 GB（實測時只剩 3.5 GB 可用，Windows 已在壓縮分頁 761 MB）
    GPU  RTX 3050 Ti Laptop **4 GB VRAM**  驅動 566.07 / CUDA 12.7
    專案在 Google Drive 虛擬磁碟 G:（Windows 回報 FAT32）

### 1. homr 開 GPU 反而慢 5 倍，而且會改變辨識結果

裝 `onnxruntime-gpu` 之後 `CUDAExecutionProvider` 確實出現，homr 的
`onnx_providers.gpu_available()` 也回 True（它的 `--gpu` 預設就是 AUTO，
不用改任何程式碼就會自己用）。拿〈士兵進行曲〉page_01_prep.png 量：

    CPU（原始環境）        76675 bytes  sha1 b40d2219649e5004   42.7 秒
    GPU                    76614 bytes  sha1 d109e1e225b53c93  219.1 秒
    裝了 gpu 套件但 --gpu no  74301 bytes  sha1 c56be1568bd3d2b4   32.0 秒

三件事：

* **慢 5 倍**。4 GB VRAM 撐不住 segnet + encoder + decoder，在 CPU/GPU 之間
  反覆搬資料。**這一條是這台機器造成的**，24 GB 的卡上結論可能相反。
* **輸出不一樣**。GPU 的數值差異讓辨識結果改變，所有既有基準失效。
* **最危險**：即使強制 `--gpu no`，只要**裝過** `onnxruntime-gpu`，輸出
  還是變了（74301 vs 76675）。光是安裝這個套件就會改變辨識結果，
  而且沒有任何警告。**這一條跟硬體無關，換機器也一樣。**

移除時 pip 把共用檔案一起刪掉，留下「metadata 說已安裝、實際 import 不到」
的半殘狀態，要 `pip install --force-reinstall --no-cache-dir onnxruntime==1.28.0`
才修得回來。修完再驗一次 sha1 確認回到 `b40d2219649e5004`。

### 2. 自己訓練 OMR 模型：這台做不到

homr 官方 `Training.md` 的需求：

    訓練資料  19 萬頁 / 12 GB（PRIMUS + GrandStaff + Lieder + MuseTrainer + PDMX）
    VRAM      8 GB（batch 8）／16 GB（batch 18，預設）／24 GB（batch 32）
    時間      segnet 約 1 小時、**TrOmr 2–4 天**（單卡）
    系統      Linux + CUDA，另需好的 CPU 餵資料
    官方建議  「RTX 3090 CP 值最好」

**4 GB 連最低門檻的一半都不到，而且是 Windows。** 要做的話租雲端比買卡划算
（3090 約 US$0.2–0.5/小時，一次 3 天的訓練 US$15–35）。

但硬體不是真正的瓶頸：homr 已經用 19 萬頁訓練過，它在**乾淨排版譜上是 100%**
（André 對 Mutopia 標準答案）。失敗的是密集樂段，那不是訓練量的問題。
而且 `btrkeks/transcoda-59M` 的公開數據直接說明了 domain gap：
合成資料 18.5% 錯，**真實掃描件 64.0% 錯**。要超越 homr 需要的是大量
「真實照片 + 正確答案」的配對，那是研究團隊等級的標註工程。

### 3. Sheet Music Transformer：載入成功但輸出全部截斷

`antoniorv6/smt-camera-grandstaff`（21.4M 參數、MIT、訓練資料就是相機拍的
鋼琴大譜表）在 4 GB 上跑得動，GPU 推論 37–53 秒/system。但：

    config 的 maxlen = 1281 token
    10 個 system 的輸出字元數全部擠在 1306–1362 之間
    沒有一個有 spine 終止符 `*-`
    8/10 個 system 讀不出低音譜號（全部 *clefG2）

長度一致但音樂內容天差地別 = 撞到硬上限。GrandStaff 訓練資料是**短樂句片段**，
不是整行。**這一條跟硬體無關。**

要繞過得切成 1–2 小節餵，但 37 秒/次 × 一頁 36 次 ≈ 22 分鐘/頁，李斯特 13 頁
要 5 小時。不實用。

環境建在 `C:\piano-ml`（獨立 venv + torch cu126 + SMT repo checkout 到
`fdeb7c3`），**沒有動到專案的 `.venv`**。

**載入 SMT 的地雷**：HuggingFace 上的權重是 2024-08 存的，模組名是
`cross_attention.lk/lq/lv` 與 `ffNet`；GitHub main 在 2025-02 的 `2c29df4`

而它只印一行 warning 就繼續跑 —— 會產出看起來正常、實際是雜訊的結果。

### 4. Unity 專案不能放在 Google Drive 上

`G:` 是 Google Drive 的虛擬磁碟，Windows 回報 **FAT32**。Unity 的 AssetDatabase
是 LMDB（記憶體映射）實作的，在上面直接崩潰：

    LMDB_Map::Set → SourceAssetDBWriteTxn::RefreshStage3_OverlayDirtyAssets
    → AssetDatabase::InitialRefresh

`%TEMP%\Unity\Editor\Crashes` 裡 2026-08-14 就有兩份同樣的崩潰報告。
原本的 `音遊` 專案之所以還能開，是因為它的 `Library` 是從 OneDrive 整包搬過來、
沒有在 G: 上重建過。

**解法**（已套用）：專案外殼放本機 NTFS，原始碼用 junction 接回 Google Drive：

    C:\UnityProjects\音遊GD\Assets|Packages|ProjectSettings  -> junction -> G:\...\音遊\
    C:\UnityProjects\音遊GD\Library                          -> 本機，不同步
    C:\UnityProjects\data                                    -> junction -> G:\...\data

這樣原始碼有雲端備份與版本紀錄，1.5 GB 的快取留在本機不佔配額。
**Python 側完全不受影響** —— 它只是一般檔案讀寫，不做記憶體映射。

⚠ `C:\UnityProjects\音遊GD` **不能**用 `Remove-Item -Recurse` 整個刪，
裡面三個 junction 會讓它跟著吃掉 Google Drive 上的原始專案。要刪先用
`[IO.Directory]::Delete(path, $false)` 單獨移除連結。

### 5. Bach 平均律那份 PDF：任何引擎都救不了

不是機器問題，但同屬「不用再試了」的一類，記在這裡免得重踩：

    PDF 頁面尺寸  180.8 x 275.6 pt = 2.51 x 3.83 英吋（其他 PDF 都是 595–842 pt）
    300 DPI 渲染  754 x 1149 px，**行距 6 px**

提高 DPI 沒用 —— 清晰度（Laplacian 變異數）隨 DPI **下降**：
300dpi 2337 → 600dpi 502 → 1200dpi 78，證明內嵌影像本身就沒有更多細節。
`project._split_pdf()` 寫死 `scale=300/72`，對正常頁面沒問題，
但這份的頁面框異常地小。**要修只能換一份掃描**（IMSLP 上 WTC 有多個版本）。

它一首佔全部小節的 24%，是整體可靠度最大的單一缺口。

## 2026-08-15 — 「左手全都被當成右手了」：把壓扁的大譜表拆開重辨識

User: "像是士兵進行曲，左手全都被當成右手了". 在音遊裡看得到 —— 左右手是用顏色
分的（右手藍 `0.22,0.51,0.96`、左手橘 `0.94,0.55,0.12`，黑鍵再壓暗 0.55 變棕色），
整首同一個顏色就是分手失敗。

### 不是大括號沒認出來

    辨識結果   score-part "Voice"（不是 Piano）、沒有 <staves>2</staves>
               33 個小節、259 個音**全部掛在 staff 1**，譜號在同一行 F/G 跳來跳去

第一個猜測是 homr 沒看到大括號。跑它自己的診斷，**猜錯了**：

    Found 11 staffs
    Found 6 connected staffs (after merging grand staffs, multiple voices): [1,1,1,1,1,1]

每個系統都只剩一個 Staff，表示上下兩行**已經被 merge 成大譜表**了；
`--write-staff-positions` 寫出來的座標也有 5 個 class=1 的框。teaser 圖上每個
系統的框也確實罩住兩行。大括號那一關是過的。

真正失敗的是 **transformer 的解碼**：`music_xml_generator._voice_has_two_staves()`
看的是「有沒有任何符號的 position 是 lower」，這張圖一個都沒有。模型把下面那行
的內容也解成上面那行，只是中途換譜號 —— F/G 交替就是這樣來的。那是模型的失誤。

### 作法：拆成兩張單行譜，各辨識一次

新的 `src/score_input/grandstaff.py`：

    1 跟 homr 要譜表座標（--write-staff-positions），class=1 的框就是大譜表
    2 每個框內找「墨水最少的那一列」當上下行的分界
    3 上行全部堆成一張圖、下行堆成另一張
    4 兩張各送 homr 一次 —— 它對單行譜是拿手的
    5 上行的音給 staff 1、下行的給 staff 2，逐小節併回一個 part（divisions 先通分）

第 2 步刻意**不去找十條譜線**：這種背面透印的照片上
`layout._staff_line_rows()` 五個系統只認得出兩個（[1,2,1]）。而「兩行中間有一條
空白」穩定得多 —— 中間 40% 裡墨水最少的那一列，五個系統全部切對。
**幾何要跟 homr 拿，不要用我們自己的** —— 它的譜表偵測在這張圖上是準的。

### 三道防線，避免越修越糟

| 條件 | 為什麼 |
|---|---|
| positions 檔要有 class=1 的框 | 真正的單行譜（長笛獨奏）不能被硬拆成兩半 |
| 上下兩份的**小節數要一樣** | 對不齊的話左右手整段錯開，比全部當右手更糟 |
| 音符數至少留住 **80%** | 見下 |

第三道是實測逼出來的。〈拍照測試〉第 1 頁切出來的下行太窄，homr 丟
`No staffs found`，另一邊也只認出 2 個小節 —— 合起來 217 個音剩 63 個。
**分手是分出來了，但曲子少了七成。** 加上這道之後它退回原本的結果並誠實說
「大譜表被壓成一行」。

## 2026-08-14 — 李斯特 鐘：8va 一個都沒讀到，全曲四成的音低了一個八度

User: "你先專注把李斯特 鐘修好". 上一則紀錄把它歸成「引擎的天花板」。
**那個判斷是錯的** —— 真正的原因量得出來，而且修得掉。

### 診斷：兩個具體的原因，不是「天花板」

    homr 產出的 <octave-shift>   0 個
    譜面上印的 8va               49 條
    第 1 小節宣告的拍號          7/8   （紙上印的是 6/8，管到第 60 小節）

〈La Campanella〉的招牌就是那個高音鈴聲，整首右手幾乎每一行都掛著 `8va`。
**homr 完全不產生八度記號**，所以那些音全部照紙面的寫法輸出 —— 低了一個八度。
音域 27–96 就是這樣來的；正確的鈴聲音是 D#7 = MIDI 99，我們卻輸出 D#6 = 87。
這不是「大致認得到、節奏壞掉」，是**四成的音高整個錯**，聽起來當然奇差。

### 8va 讀不到 —— OCR 這條路是死的

整頁 OCR 在 13 頁上**一個 8va 都沒讀到**（第 1 頁整頁只認出 22 個文字塊，
沒有一個是它）。8va 是斜體粗體加上標的花體字，文字偵測器根本不當它是字。
`rules.read_page_symbols()` 裡那條 `_OCTAVE_UP` 因此從來沒有命中過。

改走影像。`layout.find_ottava_lines()` 找它後面拖的**虛線**：

    一節  17 x 5 px（行距 21）= 0.81 x 0.24 個行距，扁扁的一小槓
    判準  高 < 0.35、寬 0.4–1.6、**寬/高 >= 2.2**、同列 ±0.3、間隔 < 2.2
          至少 4 節、跨 4 個行距

三個門檻是量出來才對的，不是猜的：

- 第一版把高度上限訂 **0.22**，實測是 0.24 —— **一條都找不到**。
- 沒有「寬/高」這一關的話，音符上方那排**斷奏點**會被串成線（它們也等距等高）。
  點大約 1:1，虛線的一節 3.4:1，分得很開。
- **譜線不會被誤認**：一條譜線是**一個**橫跨整個系統的連通元件，寬度遠超過
  1.6 個行距，第一關就掉了。虛線則是一節一節分開的。

### 擋掉 (accel) —— 一模一樣的虛線

`(accel)` 與 `(rit.)` 的延續線在影像上跟 8va 的線**完全一樣**。第 8 頁一次
找到 6 條，其中 2 條是 (accel)。

分得開的是**左端那個字**。量了 12 個樣本：

    8va       一個連通元件 1.52 x 1.90 個行距，頂端固定在線上方 0.43–0.48
    (accel)   最高的元件只有 0.71 x 1.67（小寫字母的上伸部）

兩群完全不重疊。所以規則是「左端要有那個字」，沒有就不算。
順帶一提，把那一小塊裁下來放大 6 倍再 OCR 是讀得到的（`cel).` / `qva-`），
但那不夠穩；量字形穩得多。

### 方向：鉤指向它要修飾的那一行

`8va` 寫在譜表**上方**、`8vb` 寫在**下方**，而虛線末端的鉤**永遠指向它要修飾的
那一行**。字讀不到，鉤是唯一不用讀字就分得出上下的訊號。

三件在這裡踩到的事：

1. **不能取「最近的一行」。** 系統之間的空白很寬，而 8va 要畫在一大堆加線的
   音符上方，所以寫在**下一個系統**上方的 8va 常常離**上一個系統**的低音譜表
   更近：第 1 頁那條 `8va scherzando` 距上一行 5.4 個行距、距它真正要修飾的
   下一行 11.0 個。取最近的會把每一條都變成降八度 —— **剛好反過來**。
2. **鉤只能看右端。** 左端是那個「8va」的字，去那裡找「又細又高的一豎」會挖到
   字的筆畫：第 8 頁那條就被判成「鉤朝上」，整段變成降八度。
3. **鉤必須碰到線本身的高度。** 少了這一條，末端窗口裡任何細長筆畫（右邊界的
   小節線、旁邊的符桿）都會被當成鉤。
4. 沒有鉤（線延續到下一個系統、或末端被裁掉）就取**下面**那一行、往上八度 ——
   8va 寫在上方是常態，8vb 少見而且幾乎都會畫鉤。

### 對到小節：兩個位置差一格的坑

- **跨度從「字」開始，不是從第一節虛線開始。** 用第一節虛線當起點，每一段都會
  少算最前面那一個小節（第 1 頁第 5 小節就是這樣漏掉的）。
- **右手/左手用 `index % 2`**，不要用小節框的上下半、也不要用 `_group_systems`。
  兩種「聰明」作法在第 3、9、10、12 頁都把兩個系統併成一個，於是下一個系統的
  **高音**譜表被標成左手 —— 那會讓 9 個小節的左手憑空高八度。鋼琴譜是大譜表，
  一頁的譜表數是偶數、兩行一組，直接數就好。

### 使用者發現的：左右手撞在同一顆鍵上

「傳說有很多左右手按鍵同時疊在一起」。Measured it — うまぴょい伝説 had **5 組**
where both hands strike the same key at the same instant, plus 6 same-key overlaps.
Every other song was clean, so it was specific to that arrangement.

Two bugs in `_trim_same_key_overlaps()`:

1. When two notes share the same `t`, `limit = nxt.t - MIN_GAP` lands **before**
   `cur.t`, so the "shorten the earlier note" branch clamped it to `MIN_DURATION`
   (0.05 s) and left a stub still sitting on top of the next note. Piano arrangements
   routinely double a melody note into the left-hand chord, but **one finger presses
   one key once** — those must be *merged*, not shortened.
2. `MIN_DURATION` (0.05) fought `MIN_GAP` (0.03): two strikes 33 ms apart leave no

## 2026-08-13 — Measure mapping and tempo map: うまぴょい伝説 27 → 180 boxes, 1 → 8 tempi

The two defects the user found are fixed, and verified against a new 8-piece
calibration set rather than against the one song.

### The anchor: the numbers the engraver already printed

Pure geometry could not separate a single-staff barline from a note stem — a stem is
3.5 interlines, a staff is 4, and the previous attempt (both ends flush with the
staff) let stems through and blew André up from 47 measures to 93.

So stop guessing from pixels. **Every printed score numbers its systems**, and our
own OCR reads those numbers cleanly:

    p1  1, 7, 15, 20, 23, 26, 29, 33, 39, 44
    p2  50, 56, 62, 68, 71, 74, 77, 80, 84, 90
    p3  95, 102, 108, 113, 117, 121, 127, 131, 136, 144
    p4  149, 156, 162, 167, 173

That is information **on the page**, read by the system itself — not a lookup. It
gives the exact measure count per system, which is precisely what barline detection
was failing to provide.

`layout.py` now runs three tiers: **printed numbers** decide how many measures a
system holds → **barlines** subdivide it → **even division** when the barlines
disagree with the count. The system a measure belongs to is therefore always right;
only the cut points inside a system are interpolated when barlines fail.

### It has to choose between two paths, because neither wins everywhere

Staff-line frames + printed numbers beat the old barline-only path on single-staff
music (27 → 180 boxes) but lose on pages where staff-line detection is weak
(〈士兵進行曲〉: 21 → 9). So `detect()` computes both and picks: printed numbers are
used only when **≥3 of them cover ≥half the systems** (1–2 system pages excepted,
where the page boundaries pin them down). Otherwise it runs the old path untouched.

Four things were needed to make the numbers usable:

- **Grand staves get merged back.** `_group_systems` splits a piano system into two
  staves; a barline spans both, so a barline system covering several staff frames
  merges them. Without it André read 14 systems instead of 8.
- **Bogus numbers rejected.** 〈士兵進行曲〉has no printed bar numbers and OCR
  assembled "531" out of fingering digits. A single unverifiable number now discards
  the whole layer — a wrong anchor is worse than no anchor.
- **Both page edges supplied.** The first system is never printed "1", and the last
  has no following number to subtract from. The pipeline passes `first_measure` (page
  1 = bar 1) and `next_first_measure` (next page's first, or total+1 on the last page).
- **Small pages upscaled.** Page 4 is 771×494 at interline 6; staff detection dropped
  lines and found 1 staff instead of 5. Anything below interline 9 is now scaled up
  to 12 first.

### Tempo map (`tempo.py` + `chart.py`)

うまぴょい伝説 prints **8 metronome marks**; the system used one for all 180 measures.
`marks_on_page()` now scans the whole page and maps each mark to a measure by **x and
y** — three of the marks share the first system, so matching on y alone collapses
them. `chart.py` gained a `_Clock` that integrates piecewise instead of multiplying
by one rate. Chart JSON still stores absolute seconds, so **Unity needed no change**.

Two distinct tempi cannot take effect at the same instant, so when interpolation puts
two marks in one cell the later one moves to the next measure rather than overwriting
the earlier — otherwise that tempo vanishes silently.

    速度地圖  115 → 105 → 100 → 121 → 170 → 167 → 110 → 170

User asked to raise the AI's confidence and its recognition success rate. The
confidence numbers really were bad — Alkan **0.30**, André **0.59** — and both of

    André   33 measures wrong by exactly **-2.0**, 4 more by exactly -3.0

Errors that land on one value are not misreadings. Each was **one** mistake:

- **Alkan**: the page prints a triplet in bar 1, and homr's entire output contains
  **zero `<time-modification>` elements**. Three eighths written as 1.5 beats instead
  of 1 is +0.5 — every measure, exactly.
- **André**: bar 25 is where "Rondo / Allegretto" starts and the printed time

### `src/score_input/repair.py`

Two repairs, driven by the hard constraint that engraved measures obey their meter:

1. **Unmarked triplets** — a measure over by exactly the duration of one note, with
   three equal consecutive onsets of that duration, becomes a triplet: durations
   ×2/3 plus `<time-modification>`.
2. **Wrong time signature** — a run of measures agreeing on a length that isn't the
   declared one gets the declared one rewritten.

**The order matters and getting it wrong is silent.** The first version ran the time
fix first, and it "repaired" Alkan's +0.5 by declaring **9/8**. Every measure then
matched its signature, Gate B went quiet — and the music was still wrong, because
note onsets come from `<duration>`, not from the meter. Validation passed while the
defect survived, now invisible. Triplet repair changes the music; time-signature
repair changes the label. Always try the former first.

### Three bugs inside the repair, all found by measuring

homr writes a grand staff **interleaved** — staff-1 note, `<backup>`, staff-2 note —
so nothing about it can be read off document order:

1. *Searching document order for three adjacent equal notes* found nothing at all;
   triplet members are never adjacent in the file. Fixed by scanning **cursor
   positions**, which is the actual time axis.

### The new song exposed a note-recycling bug in the game

candidate and `CheckMisses` then scored it Miss.

User: "開 auto 還是有 miss". Every static check on the chart data came back clean —
0 same-key overlaps, 0 zero-length notes, 0 out-of-range pitches, 0 same-pitch pairs

### Why the tests could not see it

Batch mode runs at thousands of frames per second, so `SongTime` advances well under a
millisecond per frame. The real editor runs at ~60 fps and hitches (GC, texture loads,
a burst of note spawns) push a single frame past `goodWindow` (0.16 s). **The test
environment structurally could not produce the condition that breaks it.**

Reproduced deterministically with `Time.captureDeltaTime = 0.25f`, which forces every
frame to advance a fixed 0.25 s — larger than the judgement window — and as a bonus runs
a whole song in a few hundred frames. Against the pre-fix code all eight charts collapse
to **38–64% accuracy with 8–297 Miss each**, matching what the user saw.

### Two bugs, found in sequence

1. **Autoplay was judged at wall-clock time.** `FindBestCandidate` compared the note's
   time against `SongTime` at the moment the press happened. On a long frame the press
   lands outside the window, no candidate matches, the press is discarded, and
   `CheckMisses` then marks the note missed. The computer is not playing late — the
   frame rate is. Autoplay now supplies the note's own scheduled time
   (`_autoPressTime`), and hold releases use their scheduled release time
   (`_autoReleaseTime`); both are `NaN` for human input, which keeps the human path
   byte-for-byte unchanged.

2. **Notes were judged twice — Perfect then Miss.** Fixing (1) exposed it:
   `判定 361` against `譜面 294`. `MoveNotes` recycles a note once it falls below the hit
   line, and `CheckMisses` treated "not in `_notes`" as "nobody pressed it". On a long
   frame (or with short notes) a note is judged *and* recycled in the same frame, so the
   miss check re-judged it. `CheckMisses` now consults `PerNote` before deciding a note
   was missed.

After both: **all eight charts Perfect / Miss 0 / 100% even at 0.25 s frames**, and
`TotalJudged` exactly equals the note count everywhere.

`LagTest.cs` is worth keeping in mind as a pattern — forcing a hostile frame rate found

## 2026-08-12 — Hold notes + sustain pedal

User: long notes were being treated as single strikes (holding did nothing), and asked
for the right pedal. These are one feature, not two — on a real piano the pedal is
exactly what lets you release a key without cutting the note.

### Hold notes

Notes ≥ `holdThreshold` (0.35 s) now defer their grade until the key is released:

| Held | Result |
|---|---|
| to the end (or within `holdReleaseWindow` 0.15 s of it) | keeps the press grade |
| ≥ `holdKeepRatio` (60%) | one grade down (Perfect → Great) |
| < 60% | Miss |

`FallingNote` gained a three-state machine (`Waiting` / `Holding` / `Done`) rather than a
bare `Judged` flag. `Holding` notes must be excluded from three places, each of which
would otherwise double-count or lose a note:
- `FindBestCandidate` — a held note must not be re-pressed
- `CheckMisses` — a held note is not missed, it is pending
- `MoveNotes` — **a held note must not be recycled off-screen**; destroying it would make
  the grade disappear entirely

One judgement per note either way, so `TotalJudged == note_count` still holds.

### Sustain pedal (`SustainPedal.cs`)

`Space` (moved pause to `P` — the pedal deserves the biggest key, as on a piano), or
click the pedal drawn at the bottom-left. While it is down, releasing a key does **not**
end a hold, and `PianoAudio` uses a longer, slower-decaying clip (length ×2.6,
decay ×0.35) cached separately per pitch.

**Bug found while testing:** `SetPressed()` was documented as the entry point for a real
MIDI pedal (CC64), but `Update()` recomputed the state from keyboard+mouse every frame
and overwrote it — an external pedal would have been cancelled one frame later. Now the
external source is stored separately and OR-ed with the other two.

### The charts themselves were physically unplayable

After autoplay started holding for a note's full duration, Alkan lv2 dropped from
Perfect 379 to Great 11 / Miss 1. Cause was **in the data, not the game**: 62 notes in
that chart overlap the next note *of the same pitch* — worst case by 0.545 s. One finger
cannot hold two notes on one key, so the previous hold was necessarily broken.

`chart.py` `_trim_same_key_overlaps()` now shortens each note so it ends 0.03 s before
the next note on that key. All 8 charts: 0 overlaps. Autoplay back to
**Perfect / Miss 0 / 100% on all four songs.**

This also matters for humans — a note drawn as lasting until t=2.0 while the same key
must be struck again at t=1.85 is an impossible instruction.

## 2026-08-12 — Autoplay misses fixed; BPM detection added

### Autoplay was losing points on repeated notes

User reported Miss during autoplay. Root cause: `PianoKey.Press()` early-returns when
the key is already held — correct for a piano, you must lift before re-striking — but
`RunAutoPlay` pressed without releasing first. A repeated pitch arriving while the
previous one was still held produced **no `NotePressed` event at all**, so the note was
never judged and fell through to Miss.

Why earlier tests missed it: the demo Twinkle chart has **zero** such cases (repeats are
0.6 s apart, hold is 0.25 s). A script counting "same pitch repeating inside the
autoplay hold window" found **47 occurrences in Alkan (379 notes)**, minimum gap 0.150 s,
and 0 in all three other charts. Test material chosen for convenience hid a real defect;
the downloaded classical scores exposed it immediately.

Fixes in `RunAutoPlay`:
- `AutoStrike()` releases the key first if that pitch is currently held.
- Release pass now runs **before** the press pass, so a note due to end this frame does
  not block a note due to start this frame.
- Hold time is `d * 0.7` clamped to 0.04–0.25 s rather than a flat `min(d, 0.25)`.
- **`RunAutoPlay` moved before `CheckMisses` in `Update`.** Previously a frame longer
  than `goodWindow` (0.16 s — entirely possible while a chart loads or many notes spawn)
  would mark notes missed *before* autoplay pressed them.

Verified by running **whole songs** rather than the first 10 seconds:
Alkan lv1 189/189, lv2 379/379, 簡譜 lv1 42/42, lv2 90/90 — all Perfect, **Miss 0**,
and every note judged.

### BPM detection

Charts previously hard-defaulted to 100 BPM, so falling notes were timed wrong for
anything else. **homr emits no tempo information whatsoever** — checked three real
scores: zero `<sound tempo>`, zero `<metronome>`, zero `<words>`.

The tempo *is* on the page, just as pixels. New `src/score_input/tempo.py` reads it with
rapidocr (already installed as a homr dependency):

| Source | Example | Measured |
|---|---|---|
| notation header | `BPM=100` | 示範_簡譜 → 100 |
| MusicXML | `<sound tempo>` / `<metronome>` | present in MuseScore exports |
| metronome mark | `♩ = 96` | 示範_照片 → **96** |
| tempo word | `Moderato ma con moto.` | Andre → **121**; Alkan `Lentement` → **55** |

- Only the **top 40%** of the page is scanned; the marking is always at the start, and
  full-page OCR just pulls in fingering digits and bar numbers as noise.
- The metronome regex matches `= <number>` only — the note glyph OCRs unreliably
  (`J`, `d`, or nothing).
- Values outside 30–300 BPM are rejected as misreads.
- Tempo words carry modifiers (`molto` ×1.15, `non troppo` ×0.92, …).

**When all four fail it says so and asks.** CLI prompts interactively (falls back to
printing the fix command when stdin isn't a TTY); the web UI shows an input box on the
result card. Guessing silently would leave the game's timing wrong with no visible cause.
`run.py score chart <name> --bpm N` and `POST /api/projects/<name>/bpm` both re-generate
charts and clear the `needs_bpm` flag.

Failure path verified by whiting out the top 9% of a page: detection correctly reported
nothing, and manual override at 132 then 144 BPM updated the charts and the manifest.
Out-of-range values are rejected.

## 2026-08-12 — OMR accuracy finally measured (was the top open item)

User asked me to find scores online to test with. Used it to close the item every
previous entry flagged as unverified: **note-level OMR accuracy had never been measured**.

### Ground truth

[Mutopia Project](https://www.mutopiaproject.org) publishes each piece as PDF *and*
MIDI generated from the **same LilyPond source**, so the MIDI is the correct answer for
that PDF. That is the whole reason this measurement is possible — Wikimedia scans (what
I used before) have no ground truth. Two pieces downloaded into
`data/examples/測試用樂譜/`, both public domain.

### Results

| Piece | Pitch-content recall | Aligned match rate |
|---|---|---|
| Alkan Prélude Op.31-1 (1 page, 379 notes) | **100.0%** | **100.0%** |
| André Sonatine Op.34-I (2 pages, 571 notes, mid-piece clef changes, meter change) | **94.7%** (541/571) | 94.7% (1 wrong, 30 missed) |

**These numbers describe engraved PDFs only** — LilyPond typesetting, 300 DPI, zero
noise. That is OMR's best case, not the user's actual one (phone photos). Recorded as
such in every doc; a real figure still needs real photographs.

`tools/omr_accuracy.py` makes it repeatable: PDF → 300 DPI pages → OMR → merge →
compare.

### Two metrics, and one I deliberately rejected

- **Pitch content** — multiset overlap. Time-independent: did the right notes get read?
- **Aligned match rate** — parangonar note-level alignment (same aligner the scoring
  pipeline uses), giving matched / missed / extra.
- **Rejected: element-wise sequence comparison.** Chord note order is arbitrary and one
  missing note shifts everything after it. It scored the Sonatine at 22.3% when only 30
  of 571 notes were actually wrong. It was my first attempt and it was misleading.

### Two bugs the real scores exposed

1. **`omr_accuracy.py` silently measured the wrong thing.** I loaded the OMR MusicXML
   with `partitura` directly instead of `io_utils.load_score`, so `_ensure_fields` never
   added `is_grace`; parangonar threw, fell back to `fallback-dtw`, and reported 327
   matches instead of 541. Same input, wildly different answer, no error message.
   **Any code comparing note arrays must go through `io_utils`.**
2. **Gate B false-positived on the last page.** `SHORT_PAGE` flagged Sonatine page 2
   ("only 14 measures, others average 47") — but page 2 genuinely holds just two systems,
   because it is the end of the piece. Now exempt, the same way the measure-duration
   check already exempts the final measure.

Gate B also did its job: it caught homr reading the Alkan time signature as **17/16**,
and located the measures where the Sonatine's durations don't add up — real recognition
errors, correctly identified without any reference score.

### Architecture notes

- **Additive changes only to `PianoKeyboardUI`.** Four new members

- **Notes live in a sibling RectTransform ("NoteHighway") that copies the keyboard
  root's anchors, pivot, size and position.** That means a note's X is literally

- **Autoplay is a first-class feature, not debug code.** It's how you verify a chart
  without being able to play piano, and it's how the automated Play-mode test asserts
  the judgement path works.
- **`PianoAudio` synthesises clips on first use per pitch** — 4 harmonics with

### Architecture notes

- **`pipeline.py` is the single orchestration path.** The web layer only converts HTTP
  to function calls. Divergence between "score built via CLI" and "via web" would be a
  miserable class of bug, so there is deliberately no second implementation.
- **A project's items are ordered explicitly in the manifest**, never inferred from
  filenames at read time. Batch import picks the initial order from EXIF
  `DateTimeOriginal` **only if every file has it**, else natural filename sort
  (`page2` before `page10` — segment-wise numeric compare, not string compare).
- **Two gates, deliberately separate concerns.** Gate A = "is this photo usable"
  (pre-OMR, ~1s, pure OpenCV). Gate B = "was it read correctly" (post-OMR, pure XML
  inspection). Gate B catches what Gate A structurally cannot: a perfectly sharp photo
  misread by the model. Text notation runs Gate B too — the parser only guarantees syntax.
- **Everything in Gate A is scaled by staff interline**, estimated from the mode of
  vertical black/white run lengths. Interline, not pixel count, is what determines OMR
  success. Blur is measured **after rescaling to interline=10px**, otherwise the same
  threshold is meaningless across resolutions (the flaw in most blur-detection examples).
- **`OmrEngine` is a protocol with one implementation.** Adding Audiveris later means
  adding a class, not touching callers.
- **Result verification is audio-first** (`web/static/preview.js`). A "203 notes"
  summary tells you nothing about correctness; playing the transcription back does —
  a misread pitch is instantly audible. Piano roll and falling-note views back it up.
  Web Audio oscillators + canvas, no libraries. The falling-note view doubles as a
  preview of the Unity game and a sanity check on the chart JSON.
- **MusicXML always holds everything; difficulty filters at read time.** One score file,
  no "which copy is current" problem. Level 3 would be a filter in `difficulty.py` alone.
- **`--level` on `analyze`/`play` is purely additive** — omitting it reproduces the exact
  prior behavior. Verified against the golden baseline.

### Bugs fixed during this session (with causes — likely to recur)

1. **Chinese path breaks homr, twice.** This project lives under
   `桌面\專題\暑假\ai運算`, so both are permanent conditions, not edge cases.
   - homr's dependency `musicxml` parses its bundled XSD with no encoding argument →
     `UnicodeDecodeError: 'cp950'` on Traditional Chinese Windows. Fix: run homr as a
     subprocess with `PYTHONUTF8=1`. That variable must exist at interpreter startup,
     so setting it in-process is too late — this is *why* the engine is subprocess-based
     (which also bought per-page crash isolation).
   - `cv2.imread` cannot open non-ASCII paths, and reports
     `"The file format is not supported"` — the message points nowhere near the cause.
     Fix: stage the image into an ASCII temp dir, run there, copy the result back.
     `quality.py` avoids this by using `np.fromfile` + `cv2.imdecode` throughout.

2. **Merged MusicXML unreadable by partitura** — the risk flagged in the plan.
   homr transcribes page by page and picks its own `<divisions>` per page (observed 2
   and 4). Concatenated, one part carries two time grids and partitura refuses:
   `"Note array from parts with multiple divisions is not supported"`.
   Fix: `_normalize_divisions()` takes the LCM of all values and rescales every
   `duration`/`backup`/`forward`/`offset`. LCM specifically, so the factor is an
   integer — a fractional factor would round dotted notes and triplets off-grid.

3. **Gate A had its pipeline order backwards.** Originally: detect staves → measure skew.
   But the horizontal morphological kernel doesn't preserve tilted staff lines, so a
   15°-rotated photo measured 0.0° skew, 0 staves, and reported the useless
   "no staff found" — burying the actual cause. Fix: measure skew from the raw ink
   image → deskew → then detect staves. After the fix the 15° test image measures
   exactly **-15.00°** and all 8 staves come back.
   Also added root-cause suppression: when blur / too-small / too-skewed / too-dark /
   perspective is detected, the consequent "no staff found" is no longer also reported.

4. **White paper counted as overexposure.** Clipping was measured as pure-black **or**
   pure-white pixels, but sheet music is white paper — a perfectly exposed scan is
   mostly 255, and the control image was flagged `warn` at 73%. Fix: glare is now
   measured by walking each detected staff line and finding stretches that are
   "bright and empty where a line should be"; dark clipping is counted separately.

5. **Notation auto-detection misfired.** Letter notation `C4 C4 G4 G4` has a digit per
   note (the octave), so digit-counting classified it as jianpu. Fix: count only digits
   **not preceded by a note letter**.

6. **Line breaks didn't imply a bar line**, so the last measure of one line merged with
   the first of the next and reported a bogus "8 beats in a 4/4 measure".

7. **Cross-barline ties inflated the previous measure.** Tie merging ran before measure
   validation, so the tied-into duration was attributed to the earlier measure.
   Fix: validate measures first, then merge ties.

8. **CSS: the whole UI was unclickable.** `.viewer` is `position:fixed; inset:0;
   display:grid`, and that `display` overrides `[hidden]`'s `display:none` — the hidden
   modals stayed invisible but intercepted every pointer event on the page.
   Fix: `[hidden] { display: none !important; }`. **Found only by automated
   screenshotting** (Playwright click timed out with "intercepts pointer events");
   the API tests all passed. Worth screenshotting any UI before calling it done.

### Architecture notes

- **All UI is generated at runtime.** No prefabs, no art assets. Sprites are drawn in code
  (`UIShapes`) as 9-sliced rounded rects, so stretching doesn't distort corners.
- **Single input path** — this is the key design property. Mouse clicks, computer keyboard,
  and `PressNote(midi)` all funnel through `PianoKey.Press()` → `Pressed` event →
  `PianoKeyboardUI.OnKeyPressed()` → `CharacterHopper.TeleportTo()`. Adding a new input
  source (e.g. MIDI) requires no change to teleport logic.
- **Public API for external input:** `PressNote(int midi)`, `ReleaseNote(int midi)`,
  `GetKey(int midi)`, events `NotePressed` / `NoteReleased`.
- **Range presets:** 88 (A0–C8, 52 white) / 76 (E1–G7, 45) / 61 (C2–C7, 36) / 49 (C2–C6, 29),
  or Custom. Default 88. Notes outside the built range make `PressNote` return false silently.
- **Auto-fit width is required at 88 keys** — key width = canvas width / white key count.
  At 1920px: white 36px, black 21px, character 54px. Black/white ratios 0.58 / 0.63 (real piano).
- **Chord policy: highest note wins** (default). `_heldNotes` HashSet tracks held notes;
  character sits on the max. On release it falls back to the next highest still held;
  if nothing is held it stays put.
- **Edit-mode preview:** `[ExecuteAlways]` + deferred build via `EditorApplication.delayCall`
  (can't create objects directly in `OnEnable`/`OnValidate`). Generated objects are tagged
  `HideFlags.DontSave` so they never enter the scene file. `Clear()` finds leftovers **by name**
  (`GeneratedRootName`) because private refs are wiped on domain reload — without this,
  every recompile stacked another keyboard.
